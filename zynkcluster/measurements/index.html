ZynkCluster: First Measurements
Technical note · 29 October to 2 November 2026
What happened when a 63 GB model was split across a desktop and a laptop on a home network
Summary · Setup · WiFi vs wire · The 63 GB model · Prompt reading · What this does not show · What's next

Summary

Between 29 October and 2 November 2026 we ran the simplest possible version of ZynkCluster: no custom code, just llama.cpp's RPC mode, which lets one computer hand some of a model's layers to another computer over the network. The two machines were a desktop with 62 GB of memory and an RTX 3090, and a laptop with 16 GB of memory and no usable graphics card.

Three results. First, a 63 GB model (gpt-oss-120b) answered questions while split across the two machines, with the desktop's graphics card deliberately limited to the share a 16 GB card would hold. Neither machine could have run it alone. Decode speed was about five words per second. Second, over WiFi the network dominated the cost; over a direct cable it all but disappeared. Third, the remaining cost is reading the prompt, not writing the answer, and llama.cpp's built-in prompt cache removes that cost for a repeated context with no new code.

This is a measurement note, not a product announcement. Each configuration was run once, on one pair of machines. The section What this does not show is part of the result.

Why WiFi was slow. Not bandwidth. The RPC protocol exchanges about 13 small messages per word in steady state, and each one waits for a full round trip. At WiFi's 4 ms that is most of the cost; at the cable's 0.2 ms it is a few milliseconds. The wired numbers were predicted from the message count and the measured round trip before the wired runs were made, and the predictions held to within a few milliseconds.

A placement detail worth 80 ms. By default llama.cpp puts the model's output layer on the last device, which in this arrangement is the laptop, and then pulls 785 KB of word scores back across the network every word. One flag (-ot 'output\.weight=CPU') keeps that layer on the desktop. Over WiFi that was worth 80 ms per word; over the cable, 21 ms.

How much a weak node should hold. A sweep from 2 to 12 laptop layers on the wire showed each layer moved to the laptop adds about 5.6 ms per word to decode, with no measurable fixed cost per hop. On prefill the laptop was about seven times slower per layer than the desktop. The lesson is to give a weak node as few layers as possible, which is configuration, not code.

The 63 GB model across both machines

This is the test the whole idea rests on: a model larger than either machine's memory. gpt-oss-120b is 63.4 GB with 36 layers. The desktop has 62 GB of memory. The graphics card was limited to 8 layers (about 14 GB), because 16 GB is what a current mid-range card holds and a 24 GB card is not representative. The laptop took 6 layers over the cable; the desktop's memory held the other 22.

MeasureResult
Model load218 s (63 GB read from disk; 10 GB of layers sent to the laptop and cached there)
Prefill, 117-token prompt48 s
Decode196 ms/word, 5.1 words/s
Answercoherent

The desktop alone could not do it. Attempting the same model on the desktop without the laptop, about 48 GB of model in about 42 GB of free memory, froze the machine; it had to be power-cycled. That is the control result, and it also taught us the practical rule for a node: count about 50 GB of model per 64 GB of memory, not 64, because the operating system and the model's working buffers need the rest.

Prompt reading is the real cost, and it can be cached

Every split made the answer start later, even when the 3090 held most of the model, because the laptop's share of reading the prompt runs on the laptop's slower processor while the desktop waits. With a 3,455-token prompt, the kind of context a household assistant would send along with a question:

The second-time column is llama.cpp's prompt cache (--prompt-cache): the processed prompt is saved to a file after the first run and loaded on the next. It worked over the split exactly as it does on one machine. For an assistant whose system prompt and memory context change slowly, the 85 seconds is paid when the context changes, not on every question. No new code was needed for this.

What this does not show

  • One pair of machines, one run per configuration. A three-repetition benchmark agreed with the timed runs for the CPU-only split; nothing else was repeated.
  • A laptop is not an office tower. Its memory is a third the speed of the desktop's and its processor is weaker. The plan's target hardware, used towers with two memory sticks each, has not been measured.
  • This is a layer split, not the expert split described on the main ZynkCluster page. Layers took turns; the parallel-expert architecture that could be faster is unbuilt, and these numbers say nothing about it.
  • Speeds are for 4-bit versions of two specific mixture-of-experts models. A dense model of the same size would be several times slower per word.
  • Security was not addressed. llama.cpp's RPC server is unauthenticated and its own documentation says never to expose it. These runs were on a direct cable between two machines in one room. Nothing here should be run on a shared network as-is.
  • One benchmark tool disagreed with the timed runs for the graphics-card-plus-laptop configuration and was not investigated; the timed runs are the numbers reported.
  • Load times include reading the model from disk and, on first use, sending the laptop's layers across the link. They are not steady-state figures.

What's next

The next step in the plan is the same measurement on two or three used office towers, wired, so the per-machine cost model can be checked on the hardware the idea is actually about. After that, the questions are engineering rather than research: give weak nodes few layers, keep the prompt cache warm, put the link behind proper authentication, and make the setup something a careful person can do without reading a plan document.

Full write-ups with exact commands and logs are kept with the project's working notes. The plan document in the repository carries the same numbers in context. Measurements by Matthew Skillman with Claude (Anthropic) running and recording the tests.
